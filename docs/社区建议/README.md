# 社区建议汇总

**唯一入口。** 无论谁在哪个社区征求建议（B 站 / 小红书 / QQ 频道 / QQ 群 / KOOK / Steam 工坊），
回收都只落在这一个文件里。目的只有一个：**让"收到了什么、谁处理"有据可查**——散在四个平台评论区的建议等于没征求。

## 怎么记

一行一条，追加在下面的表里，不要开辟第二个文件：

| 日期 | 渠道 | 建议（原文摘要） | 出处 | 状态 | 归属 |
|---|---|---|---|---|---|
| … | … | … | 链接或文件路径 | 待评审 / 已采纳 / 已拒绝 | 见下 |

- **出处必须有**：链接（带必要参数，例：小红书链接必须整条带 `?xsec_token=`）或本地素材路径。
  写不出出处的条目**不许进表**——那和"我听说有人想要"没有区别。
- **状态只有三态**，并且要能追下去：
  - `待评审`：还没人看过。
  - `已采纳`：**必须指向去向**（任务 id / commit / PR），否则不算采纳。
  - `已拒绝`：**必须写理由**，并且理由要能对上《接/不接判据》里的某一条闸（见下节）。
- **归属是独立的第六列，不要塞进状态**（2026-10-13 定）。理由：`待归属` 与三态是**两个维度**——
  一条建议可以既"待评审"又"受归属阻塞"，也可能"已采纳"却卡在没人提交。混成一列，状态机迟早会漂。
  取值：
  - `bin2_extension` → @bin2_extension_mod_dev 负责，**24 小时内**给「接/不接 + 理由 + 粗估工作量」。
  - `bin2_npc_extension` → **归属已于 2026-10-13 解决**：v0.5.0 由仓库所有者 lotosbin 亲自提交（`4b8f5e5`，
    其后修复 `25926da`），该目录零未提交、与 `origin/main` 一致；临时兜底分支 `backup/npc-extension-v0.5.0-20261013`
    已按约定删除。**此后这条线的建议按正常 `bin2_extension` 口径走**（不再标 `待归属`）。
  - 其他/不确定 → 留空，由 @human 定。
- **一日多条建议**：每条占一行，不合并；合并之后就找不回来是哪个人提的。
- **快照与隐私**：评论/回帖会被删被改、链接会失效，所以出处可以是「链接 + 抓取到的原文快照文件」。
  但快照**只存原文 + 链接 + 抓取时间**，不要把整页 HTML 或大图塞进仓库；
  入库前**脱掉用户名/头像/uid 这类他人个人信息**——社区建议不需要带个人数据。
  小红书没有单条评论的固定链接，最小定位用「**笔记链接 + 评论 id + 原文首句**」。
  评论 id（DOM 里就是 `comment-<id>`）是**内容级定位符**，比"第几楼"稳——楼会被删、会变，id 不会。
  工具：`小红书分享/查看笔记评论.js`（**纯只读**：`--dump` 只输出 序号/评论 id/日期/原文，**不读昵称、uid、头像**）。
  **该工具 2026-10-13 新增 `--expand`**：原先 `--dump` 只读到 **5/7**，差额正是 `[2]` 下面折叠的「展开 2 条回复」——
  **是"对账"这条规矩抓出来的**（读到的条数 vs 页面自报条数），不是有人顺手发现；展开后 **7 = 7**（只点"展开"类控件，不点赞/不回复/不关注）。
  **另一条给后来者**：`--note <noteId>` **只给 id 必 404**（`error_code=300031`），必须整条带 `xsec_token` 的链接。
  **一处两把尺子不一致（未定）**：作者侧列表把本篇评论读成 **1**，而公开页自报 **7**、工具也读到 7 ——
  可直接用的推论是**回收评论数不能拿作者侧那个数当准，要读笔记页**；**成因不猜**。
  读到的条数要与页面自报的「共 N 条评论」对账，**不一致时必须说明，不许默默截断**。

## 接 / 不接判据（技术侧，可拿去回答评论）

由 @bin2_extension_mod_dev 于 2026-10-13 给出，各渠道**可以直接引用**，不必每条都来问一次：

**接**：「原版某个东西玩家本来应该能自己做，但游戏里**没有任何路径**」——能说清游戏内名称或行为就行，不需要懂脚本。

**不接**（四条，也是 `已拒绝` 的理由口径）：
1. 改平衡数值（伤害 / 价格 / 掉率）；
2. 把别的模组整包合并；
3. 需要从零画美术；
4. **会形成材料循环的做法**。

**第 4 条的关键闸门（加配方前必查）**：能不能"回炉"？
**回炉产出 ≥ 配方消耗 = 拿 1 块料刷无限成品 → 一律拒**，并在表里写明理由。
1.7.0 那 5 条就是按这道闸过的（螺母螺栓无回炉标签、圆锯片按 1 金属板 = 4 钢块持平、螺丝产出 6 低于回炉门槛 10）。

**已有的「已拒绝」清单**（命中就直接判 `已拒绝`，不必重新讨论；出处：`bin2_b42/Changelog.txt` 1.7.0 段「刻意不做」）：
小手锯条（与手锯条重复且都能回炉）、纽扣（骨珠可替代）、武器刀刃 KillerBlades / `*_NoTang`（破坏锻造平衡）、
火柴与打火机（属于搜刮设计）、鱼 / 电子 / 带状态物品（`CandleLit`、`MetalPipe_Broken` 这类是设计如此）。

### ⚠ 使用这份判据前必须知道的数据边界

"真缺口"名单里**混着一类假阳性**：钓鱼、战利品、世界里能捡到的物件**没有建模**。
所以**不要拿名单直接当卖点**——照着念会念出"能不能做鲈鱼"这种笑话。任何方向都必须逐条核过再对外承诺。

## 四条"读起来像结论"的错（都比报错坏，写下来免得重复）

1. **AppleScript 的 `entire contents` 读辅助功能树不稳定——措辞是"不能信"，不是"必然欠计/不可比"**（被 @bin2_extension_mod_dev 两次纠正后定稿）：
   同一台机、同一页面（B 站直播页），**五种形态**：
   | 谁 / 何时 | 最前应用 | 路径 | 元素 | role 读到 | 失效 | AXButton | 耗时 |
   |---|---|---|---|---|---|---|---|
   | 组长 10:53:53 | 未记 | `entire contents` | 468 | 0 | 468（100%） | 0 | 9s |
   | mod_dev 10:54:54 | 未记 | `entire contents` | 469 | 314 | 155 | 2 | 53s |
   | mod_dev 10:55:59 | 未记 | `entire contents` | **209** | 209 | 0 | 16 | 26s |
   | 组长 10:57:07 | 未记 | `entire contents` | 381 | **0** | **381** | **0** | **8s** |
   | mod_dev 10:58:03 | **Safari** | `entire contents` | 383 | 381 | 2 | **13** | 37s |
   | mod_dev 10:58:03 | **Safari** | ctypes 直接 AX API | 385 | — | — | **13** | 0.07s |
   → **最后两行是决定性的反例**：同页同分钟，**两条路径给出的按钮数完全一致（13 = 13）**，路径 B 一点没欠计。
   **所以正确措辞是"不可靠"**：它**既可能完全一致，也可能全失效到 0**；写"跨路径不可比"会让下一个人
   **把真正的不一致当成正常现象放过去**，写"必然欠计"则是把反例当不存在。
   → **行动结论不变且更硬**：判"按钮在不在"**用直接 AX API**（0.07–0.15s，稳）；`entire contents` 只做回退，
   **且必须把"失效数"和按钮数一起报**（否则"欠计"看起来就像"没有按钮"——那场争论的起点）。
   → **未分开的变量（不要写机制）**：① 最前应用是谁 ② 窗口是否 `AXMain` ③ 页面活性 ④ **失效节奏**
   （8s 全失效 ~20ms/元素 vs 37s 几乎全成功 ~100ms/元素——"立即失败"与"走一半失败"可能是两种机制）。
   **要分开它们，用静态页**：下一篇 stage 好的发布页**不自动刷新**，是最合适的样本。
   实验设计（@bin2_extension_mod_dev 定，我采纳）：
   - **由把页面摆出来的人喊那一声**——发布页只能 @小红书运营 来 stage，**别人不该重开一张已发布的笔记**
     （会造出可能被误按的重复稿，他已经拒绝过一次，理由正确）；他摆好后**同一分钟喊两人**。
   - **四条读数交错跑：A、B、A、B，不要 A、A、B、B**。按组跑时，中间任何一次页面变化都会**伪装成"路径差异"**；
     交错跑才能让两条路径**共享同一个时刻窗口**（这也是 10:58 那组能定案的原因）。
   - **判据（@bin2_extension_mod_dev 提，我采纳并加一条前提）**：B 的读数**只有被 A 夹住才算数**——
     实际形态是 A1(0.1s) → B1(可能 8–53s) → A2(0.1s) → B2；**B1 合法当且仅当 A1 = A2**，
     A1 ≠ A2 时 B1 直接作废（那几十秒里页面动过，分不出"路径不稳"还是"时刻不同"）。A 只要 0.1s，正好当稳定期探针。
     - **但"A1 = A2"不能按精确相等判——先量 A 自己的抖动带**（组长 11:07–11:08 实测，纯只读）：
       · **同进程连读 15 次**：win1（B 站直播间）元素 **410×1，其余 411×14**；win2（小红书首页）**468×1，其余 469×14**。
         **两个窗口的首次读都比后续稳定值少 1**，其余 14 次零抖动。**按钮数 13 / 17，两种量法共 30 次读一次没变。**
       · **独立启动 15 次（每次只读一次）**：win1 元素 408×1 / 409×7 / 410×1 / 411×3 / 413×2 / 414×1（区间 **408–414**）；win2 468×1 / 469×14。
       → **判据分两级：按钮数相等是第一判据（最硬，30 次零抖动）；元素数是第二判据，按该页实测带子判，不按精确相等。**
       → **带子必须用"与实际读数同一种量法"测出来**（@bin2_extension_mod_dev 补，我采纳——我提带子时漏了这句）：
         那天 A1/A2/A3 是**三次独立启动**，所以判据只能取**跨进程**那组（实测：活页 **408–414**、静态页 **468/469**）；
         **拿同进程带子（410/411）去判跨进程读数，会把合法的 A1/A2 误杀**——用另一种量法的数字判这一种量法，正是这几天反复出现的那类错。
       → **A 每次读数前先做一次丢弃的预热读**，A1/A2 便都落在稳定值上，静态页上"元素数精确相等"也成立。
       → **超出带子就是"页面变了"、不许吸收进带子**（否则又变成 fail-open）。
       → ⚠ **"静态页带子为 0"被实测收窄成"同进程内为 0"**（@小红书运营 把两种量法分开量后自己作废了前一句）：
         静态的小红书首页**同进程 3 读（含 1 次预热丢弃）= 469 × 3，带子 0**；但**跨进程 4 次独立启动 = 469 / 470 / 470 / 470，带子 1**（`uuid` 全程一致、`childErr` 恒 18）。
         我这边跨进程 15 次是 **468×1 / 469×14**，同样 ±1。→ **静态页在跨进程下也有 ±1**，
         所以"保留精确相等"**只在当页现测的跨进程带子确实为 0 时才用，不许预设**——否则又是在拿另一种量法的数字判这一种量法。
         （副产品·**已按证据强度收窄**："读数前先做一次丢弃的预热读"**有时**能挡掉偏低的首读，**但不能保证**——
          我这一侧在一个进程里见过两次首读偏低（468 / 410），而 @小红书运营 两次同进程不带预热都没有偏低
          （11:08：小红书首页 **469×10 首读即 469**；B 站直播间页 **414×3 后 413×7**，掉值在第 4 读）。
          **且我那"两次"不是两个独立样本**：同一个进程、同一时刻的首次读，两个窗口只算 **n=1**。
          → 协议里**保留预热读**（便宜、无害），但**不声称它消除差异**；**跨进程那 ±1 它肯定挡不掉**。）
       → **那天的分工已经落到工具上**（@小红书运营）：A1/A2/A3 用**跨进程**模式（每条带 `uuid` + 窗口主键 + 前/后指纹）；
         "尚未进树"的单调收敛签名用**同进程**模式连读 5 次、塞在 B 与下一个 A 之间；两条命令**共用同一份窗口解析**，所以"量的就是那个标签"口径一致。
       → 上面是**读数**。**成因未定**：首次读效应、页面活性都是候选，活跃页带宽 7 / 静态页带宽 1 的迹象指向页面一侧，
         但"两个窗口的差异"不止活性一个变量——**不写机制**。（量带子的工具：`notes/verification/axband.py`，同进程/独立启动两种量法。）
       · **@小红书运营 同刻 10 连读（同进程）**：B 站直播间页 **414×3 后 413×7**、小红书首页 **469×10 全同**、按钮 13/17 全同、
         **`childErr` 恒定（16 / 18）**。三点结论：
         ① **"±1 跟着页面走"**——活页有带宽、静态首页十次一字不差（"样本必须静态页"是这条读数本身要求的）；
         ② **`childErr` 不随元素数变 ⇒ 排除"遍历偶尔少读一棵子树"这个解释**（但**不等于**"那 1 个元素确实在/不在"——
            还有第三种可能：元素已存在、那一刻还没进树，这种情况**不产生 `childErr`**）；
         ③ **他那次掉值在第 4 读、不在第一读**，而我一个进程里两次看到首次读偏低（两个窗口都是）——**"首次读效应"跨进程没有复现**，
            所以"读数前先做一次丢弃的预热读"**便宜且无害，但不能声称它一定消除差异**。
       · **那天读数必须同时记 `childErr`**：若带子非 0 而 `childErr` 也在变，那更可能是遍历问题、不是页面在动（两者不许混进同一个带子）。
       · **"元素尚未进树"有一个零成本的可判签名**（@bin2_extension_mod_dev 提，我采纳）：**页面刚发生变化之后立刻连读若干次**——
         **单调收敛到稳定值 ⇒ 支持"那一刻还没进树"**；不单调（上下漂）⇒ 支持"元素真的在/不在"。
         **前提是该页其余部分静止**（页面本身渐进渲染也会单调）；那天 staged 的静态页正合适，而这个连读正好塞在 B 与下一个 A 之间的空档里，不额外花时间。
     **前提：A 不能只记"元素数 + 按钮数"**，必须同时落**这次解析到的定位条件，且必须是两条路径都读得到的字段**：
      **`AXIdentifier`（=`SafariWindow?IsSecure=true&UUID=<uuid>`，窗口级主键）+ `AXTitle`（准入条件）+（元素数, 按钮数）**。
      - **为什么是 UUID 而不是「窗口 id / 标签序号 / 窗口 URL」**（我先前那版写错，11:02 被实测推翻）：Safari 的 `id of window` 只存在于 AppleScript 侧，
        AX 侧读不到，两边无法对齐；`AXDocument` / `AXURL` 实测**读不到**（`missing value`），所以"拿窗口 URL 当指纹"这条路不通。
        UUID 是同一命名空间里的主键——**11:02 三方独立读出同一对值**（@bin2_extension_mod_dev 两条路径、@小红书运营 `--windows`、组长 ctypes + System Events），且可复读同值。
      - **UUID 只定「哪个窗口」，不定「这个窗口此刻显示哪个标签」**（这条是组长提、@bin2_extension_mod_dev 复述确认的）：`AXTitle` 随当前标签页变，
        所以它是**准入条件**而非被比对的量——一次读数只有 `AXTitle` **包含**目标页标题时才算数（实测带前缀 `个人 — 末日第3天…`，故用包含不用相等），
        然后才拿 UUID + 计数去比。**假夹逼实例**：发布页是 win 22287 的后台标签、该窗口 `AXTitle` 是直播间页标题，此刻读它读到的是直播间页；
        若 A1、A2 都读了它 → UUID 相同、计数相同、"夹逼成立"，却是给一个量了别的页的 B1 背书。
      - **几何匹配可以彻底不用**（@小红书运营第一版靠坐标配对时，隐形窗口 `id=6005` bounds `(96,80,1728,892)` 与 `id=8181` `(96,80,1728,893)` 重合，一个 ax 项同时命中两个）。
        改用 **`AXTitle` ↔ Safari 侧 `name of current tab` 的包含关系**配对 UUID 与 Safari 窗口 id——实测两窗口逐个对上，且**一次配对同时证明「哪个标签是当前标签」**。
      - **慢路径 B 自带一道护栏**（@bin2_extension_mod_dev 补）：B 要跑 8–53 秒，**必须在自己的遍历开始前和结束后各打一次窗口标题**；
        切换发生在 B 遍历途中时，它那份树是**跨两个页面的混合体**（计数既非前者也非后者，只看首尾之外的时刻谁也发现不了）。
        **B 两端标题不一致 ⇒ 本次 B 作废，与 A 的夹逼无关。**（**状态：口径已定，尚无实测样本**——提出者本人也只认字面，那天第一次真跑。）
      - **写 ctypes 探针的三个签名坑**（组长 11:02 现场踩到前两个，都在取 `AXWindows` 那一步）：
        ① `CFStringCreateWithCString` **必须显式声明 `restype = c_void_p`**，默认 `c_int` 会截断 64 位指针 → **段错误**；
        ② `AXWindows` 返回的是 **NSArray**，**不能按字符串转**——喂给 `CFStringGetCString` 会抛 `NSInvalidArgumentException: unrecognized selector` 并带走整个进程，
        要原样走 `CFArrayGetCount` / `CFArrayGetValueAtIndex`；③ `AXUIElementCreateApplication(pid)` 是**返回值**、不是 out-param。
      - **准入还必须判「唯一」**（@bin2_extension_mod_dev 提，我采纳）：`AXTitle` 包含目标标题的窗口 **> 1 时中止并打印候选**——
        两个窗口都停在小红书首页、或同一链接开了两次，都是真实场景；此时"静默选中其中一个"等于**在按之前就把目标搞错**，与上午那次误按同形。

## 平台发布的两条坑（发帖的人踩过，写下来免得重复）

1. **B 站动态：点「发布」不等于发出。** 网页端会再弹一个「确认并发送」的规范弹窗，**必须再点它才落库**。
   @哔哩哔哩运营 第一次点完「发布」后接口里查不到新动态，正是缺这一步（`控制台/发动态.js --send` 已补）。
   —— 这是同一类病的第 N 次复发：**操作返回成功 ≠ 状态已改变**，必须回读目标状态才能宣称成功。
2. **B 站列表接口不下发正文。** `x/polymer/web-dynamic/v1/feed/space` 对图文动态**不含 `desc.text`**，
   只看列表会把一条有内容的动态误判成空动态；**要读正文得用 `x/polymer/web-dynamic/v1/detail`**。
   （判据是本机实测的接口行为，属"会变的状态"，引用前按规矩 A 重读。）

### 各平台的"我能不能独立核到"（2026-10-13 实测，供后来者少走弯路）

| 平台 | 无登录态能否核到内容 | 说明 |
|---|---|---|
| 小红书（笔记页） | **能**（裸 HTTP 即可） | 200 + `<title>` + 正文关键词 |
| B 站（动态 / 专栏） | **只在浏览器上下文里能** | 见下，别照抄"核不到"三个字 |
| QQ 频道 / QQ 群 | **不能** | 只有 JS 壳，内容前端渲染；群回复连接口都没有 |

**B 站那条要按实测口径写，不然会误伤**（@哔哩哔哩运营 复议 + 我复现 curl 侧）：

- **浏览器内、不带 cookie** 请求 `x/polymer/web-dynamic/v1/detail?id=…` → **HTTP 200 / `code:0`**，
  响应里有**完整正文**（他实测首句 / 中段 / 末句 5/5 命中）与 `visible:true`；**不是缓存**（加时间戳强制新请求仍成立，
  同一时刻带 cookie 的响应更大 185 字节，属字段裁剪而非内容不同）。
- **裸 `curl` 一律 `{"code":-352}`**（我复现过，换 Safari UA、带 Referer 无效），网页版只有 3.5 KB 前端壳页。
- **两边不矛盾**：区别在于**请求带不带浏览器的风控指纹**（UA / Referer / buvid 那类）。
  所以正确表述是：**离开浏览器核不到，原因是风控不进门，不是内容不可见。**

> ⚠ 别拿网页壳页当"看不到"的证据：动态正文本来由 JS 拉，壳页不渲染正文，**与可见性无关**。

**所以对外结论只有两档**：①「我独立核到」（附读数时间 + 命令）②「采信执行者在浏览器上下文里的回读证据」（写明是谁、读到什么）。
**B 站与 QQ 渠道归第②档**——这既没把证据说小，也没把边界说大。

> ⚠ **复核这类"找旧内容"的命令有两个静默假阴性坑，两个都实测过**（2026-10-13，同一份 68 MB 对象流）：
> 1. `xargs -n 300 git cat-file --batch` —— 对象名**只能走 stdin，不能走 argv**，git 报
>    `fatal: batch modes take no arguments`，管道里没有内容，`grep -c` 于是返回 **0**。
> 2. **locale**：对象流含 NUL 与非 UTF-8 字节，`LANG=C.UTF-8`/`LC_CTYPE=en_US.UTF-8` 下普通
>    `grep -ac` 返回 **0**，加 `LC_ALL=C` 才是 **1**（python 字节计数同为 1）。
>    **所以逐对象 `git cat-file -p <blob> | grep -q` 也必须带 `LC_ALL=C`**——它上次对只是因为命中的是纯 UTF-8 文本。
>
> 实测可用的两条命令：
> ```bash
> # 扫全部对象（含 dangling）→ 1
> git cat-file --batch-all-objects --batch | LC_ALL=C grep -ac '不做大而全'
> # 要 blob id（慢但直白，约 37s）→ da911197bfe9882c49008610192c8fb6f0c779a4
> git cat-file --batch-all-objects --batch-check | awk '$2=="blob"{print $1}' \
>   | while read o; do git cat-file -p "$o" | LC_ALL=C grep -q '不做大而全' && echo "$o"; done
> ```
> **教训一句话：一条没跑过的命令不能当"可复算命令"发出去**——下一个人会照抄，然后得到一个**自信的假阴性**。
> 这比不给命令更坏。发命令的人必须附**本机实际输出**。
