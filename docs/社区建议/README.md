# 社区建议汇总

**唯一入口。** 无论谁在哪个社区征求建议（B 站 / 小红书 / QQ 频道 / QQ 群 / KOOK / Steam 工坊），
回收都只落在这一个文件里。目的只有一个：**让"收到了什么、谁处理"有据可查**——散在四个平台评论区的建议等于没征求。

## 怎么记

一行一条，追加在下面的表里，不要开辟第二个文件：

| 日期 | 渠道 | 建议（原文摘要） | 出处 | 状态 | 归属 |
|---|---|---|---|---|---|
| … | … | … | 链接或文件路径 | 待评审 / 已接（待定去向） / 已采纳 / 已拒绝 | 见下 |

- **出处必须有**：链接（带必要参数，例：小红书链接必须整条带 `?xsec_token=`）或本地素材路径。
  写不出出处的条目**不许进表**——那和"我听说有人想要"没有区别。
- **状态四态**（第四态由我 2026-10-13 13:45 补，理由紧跟在本条之后），并且要能追下去：
  - `待评审`：**还没有可落地的结论**。它有两种形状，**第二种必须带规定的括号**（2026-10-13 15:5x 定）：
    ① 还没人判（技术侧没看过）；
    ② **已判"超出《接/不接判据》的定义域"**、等 @human 定方向 → 写成
    `待评审（技术侧 <日期> 判：不在《接/不接判据》定义域 —— 判据第 5 条，不是命中四条闸；方向与做不做由 @human 定）`
    （2026-10-13 那两行小红书就是这个模板，@bin2_extension_mod_dev 填的）。
    **只写 `待评审` 三个字是不够的**——扫这一列的人分不出"没人看"和"已经判过、卡在 @human"，而这两件事的下一步完全不同。
  - `已接（待定去向）`：**技术侧已判"接"，但去向还没定**——在等 @human 定"做不做 / 进哪个版本"，或等开出一张任务卡。
    必须同时写四样：**技术侧结论日期 + 依据 + 粗估工作量 + 在等谁**（缺一就是"悬空的接"）。
    **只有技术侧能进这一态**，渠道侧不许填；**它不是终点**：一旦出现去向（任务 id / commit / PR）**立刻改成 `已采纳`**；
    **超过 7 天仍无去向，我在 Thread 里升级给 @human**——不许安静地躺着。
    也不许拿它替代 `待评审`：技术侧还没看过的，一律还是 `待评审`。
    技术侧判"接"时若当场就能给去向（开了卡 / 有人认领），**直接写 `已采纳` + 去向，不必经过这一态**。
  - `已采纳`：**必须指向去向**（任务 id / commit / PR），否则不算采纳。
  - `已拒绝`：**必须写理由**，而理由只有两类合法（第二类 2026-10-14 19:5x 补）：
  ① 对得上《接/不接判据》里的某一条闸（见下节，技术侧判的）；
  ② **@human 定的范围/优先级决定"不做"**——必须**原文引用**他的决定＋日期，并**注明"不是命中判据闸"**
  （否则下一个人会把"他不想做"读成"撞了闸"，也会把"技术侧判过接"这件事一起读丢）。
  这两类之外一律不许填：信息不足 ⇒ 保持 `待评审` 由渠道追问；超出定义域、还没人定 ⇒ 保持 `待评审` 路由 @human。
- **为什么这一类不加"第五态"（2026-10-13 15:5x，我定的）**：第四态是因为**结论没有格子可放**才补的；
  "超出定义域"这一类**结论已经落在状态格里**（就是上面那个括号），所以**不加新状态词**——
  为整齐而膨胀状态词，下一个人就得先学五个词才能读表。**补格子的门槛是"结论会丢"，不是"格子不好看"。**
- **为什么补第四态（2026-10-13 13:45，我定的）**：第一批真实回收就撞上了"技术侧已判接、去向要 @human 定"这个状态，
  而三态里**没有它该待的格子**——后果是 @bin2_extension_mod_dev 的结论被写进了**出处格**（渠道侧无处可放，只能塞进手边最近的一格）。
  我原来说"不许自造第四态"，那句话对的是**渠道侧**（状态词不能各自发明）；**账本缺一格的代价要我来补**：
  缺格子的代价不是多一个词，而是**一条已经有结论的建议，看起来还像"没人看过"**。所以分工是：
  **状态机由我维护——想加态先说一声，不要各自发明；技术侧只负责把"接/不接"判出来。**
- **归属是独立的第六列，不要塞进状态**（2026-10-13 定）。理由：`待归属` 与三态是**两个维度**——
  一条建议可以既"待评审"又"受归属阻塞"，也可能"已采纳"却卡在没人提交。混成一列，状态机迟早会漂。
  取值：
  - `bin2_extension` → @bin2_extension_mod_dev 负责，**24 小时内**给「接/不接 + 理由 + 粗估工作量」。
  - `bin2_npc_extension` → **归属已于 2026-10-13 解决**：v0.5.0 由仓库所有者 lotosbin 亲自提交（`4b8f5e5`，

    已按约定删除。**此后这条线的建议按正常 `bin2_extension` 口径走**（不再标 `待归属`）。
  - 其他/不确定 → 留空，由 @human 定。
- **信息量不足的建议：保持 `待评审`，由渠道侧追问一次**（2026-10-13 补，第一批真实回收就撞上了）。
  三态里**没有**"需要追问"这一格，也不该有——追问**不改变状态**，因为对用户来说那条建议仍是"还没结论"。
  规矩：**判不了就别判**。若建议短到无法判断（例：QQ 频道那条全文只有 8 个字「我想要锻造耙头」，
  征集贴点名的两点都没展开），**不许填 `已拒绝`**——按本文件的规则，`已拒绝` 的理由必须能对上《接/不接判据》里的某一条闸，
  "信息不足"对不上任何一条闸，硬填就是**把一个"我没法判"包装成"我们不要"**。
  正确动作：**渠道负责人在原帖回一句追问**（问什么由技术侧说需要哪一项信息，措辞归渠道），条目**继续 `待评审`**。
  这**不违反**我们对社区说的"不承诺逐条回复"：那是**不承诺对每条都给答复**，而追问是**为了能给出结论**才做的必要一步。
- **落在《接/不接判据》定义之外的"方向性问题"：也保持 `待评审`，路由给 @human**（2026-10-13 补，第一批 3 条里 2 条就是这类）。
  判据把"接"定义成「原版某个东西玩家本来应该能自己做、但游戏里**没有任何路径**」；而"**新增玩法机制**"（例：「阅读传单触发尸群、类似藏宝图」）
  与"**新手体验/降门槛方向**"（例：「能快速入门的模组」）**都不落在这个定义里，也不命中四条"不接"**——它们是**"这类做不做"的范围问题，不是技术闸门问题**。
  规矩：**这种条目不许填 `已拒绝`**（技术侧判不了它，填了就是**替 @human 决定范围**），也不该硬塞给某个模组目录；
  **也不许填 `已接（待定去向）`**（技术侧并没有判"接"——这条归的是范围，不是工作量）。
  状态写成上面那个**规定括号**、归属留空；**不逐条催 @human**——按周合并时把这一类的条目**整批列**给他
  （他 15:5x 也已开了新 Thread 继续收创意，方向决策本来就该批量做），**卡过一周的必须出现在那一批里**。
- **⚠ 一条给 @human 的观察（第一批实测）**：已发的文案里**两条都说了**（「接」的定义 + 四条「不接」都写在正文里，发布闸门又是"正文与 `文案.md` 逐字"），
  **所以这不是话术没说清，是受众的自然倾向**——来的人更容易说"我想要什么新玩法"，而不是"哪个原版道具缺路径"。
  后果：**技术闸门会挡不住大部分回收**，真正需要的是有人定期定"方向要不要做"。两条路可选：① 接受这个形态，让 @human 批量定方向；
  ② 再收窄话术（但会降低回收量）。**这是范围与优先级的取舍，归 @human。**
- **一日多条建议**：每条占一行，不合并；合并之后就找不回来是哪个人提的。
- **快照与隐私**：评论/回帖会被删被改、链接会失效，所以出处可以是「链接 + 抓取到的原文快照文件」。
  但快照**只存原文 + 链接 + 抓取时间**，不要把整页 HTML 或大图塞进仓库；
  入库前**脱掉用户名/头像/uid 这类他人个人信息**——社区建议不需要带个人数据。
  小红书没有单条评论的固定链接，最小定位用「**笔记链接 + 评论 id + 原文首句**」。
  评论 id（DOM 里就是 `comment-<id>`）是**内容级定位符**，比"第几楼"稳——楼会被删、会变，id 不会。
  工具：`小红书分享/查看笔记评论.js`（**纯只读**：`--dump` 只输出 序号/评论 id/日期/原文，**不读昵称、uid、头像**）。
  **该工具 2026-10-13 新增 `--expand`**：原先 `--dump` 只读到 **5/7**，差额正是 `[2]` 下面折叠的「展开 2 条回复」——
  **是"对账"这条规矩抓出来的**（读到的条数 vs 页面自报条数），不是有人顺手发现；展开后 **7 = 7**（只点"展开"类控件，不点赞/不回复/不关注）。
  **另一条给后来者**：`--note <noteId>` **只给 id 必 404**（`error_code=300031`），必须整条带 `xsec_token` 的链接。
  **一处两把尺子不一致（未定，而且方向也不定）**：作者侧的「评论」数与公开页自报数**对不上，高低两个方向都见过**
  （2026-10-13 三篇同刻读数，@小红书运营 实测；格式＝作者侧 vs 公开页自报/工具读到）
  —— 征求帖 **1 vs 7/7**（作者侧低 6）、1.7.0 那篇 **5 vs 1/1**（作者侧**高 4**）、招人帖 **1 vs 2/2**（低 1）。
  → 口径：**两边不是同一把尺子、方向不定（高 4 和低 6 都出现过）、成因不猜**——
  **不许写成"作者侧欠计/偏低"**，那又是拿单点读数给一个属性下定义（本文件上方那类错）。
  **可直接用的推论不变**：**回收评论数不能拿作者侧那个数当准，要读笔记页**（三篇的笔记页读数都与页面自报一致）。
  读到的条数要与页面自报的「共 N 条评论」对账，**不一致时必须说明，不许默默截断**。

## 接 / 不接判据（技术侧，可拿去回答评论）

由 @bin2_extension_mod_dev 于 2026-10-13 给出，各渠道**可以直接引用**，不必每条都来问一次：

**接**：「原版某个东西玩家本来应该能自己做，但游戏里**没有任何路径**」——能说清游戏内名称或行为就行，不需要懂脚本。

**不接**（四条，也是 `已拒绝` 的理由口径）：
1. 改平衡数值（伤害 / 价格 / 掉率）；
2. 把别的模组整包合并；
3. 需要从零画美术；
4. **会形成材料循环的做法**。

**第 5 条（2026-10-13 补，定义域边界）**：**不是「原版缺件 / 缺路径」类**的建议——方向型、体验型、新机制型的愿望
（例：要一个新手引导向的模组、要给原版传单加"读后刷尸群"的新玩法、要改善多人体验）。
它们**不算"不接"的四条闸**，而是**不在本模组的定义域**：`bin2_extension` 做的是"原版缺了制作路径、把它补上"。
→ 这类条目**归属留空、由 @human 定方向**（可能属于合集、新模组或干脆不做），**技术侧不填 `bin2_extension`**。
→ 反过来：**只有「原版缺件/缺路径」类才填 `bin2_extension`**。判断成本很低，一句话就够：
**"游戏里有没有任何一条路能拿到它？"**——有路（哪怕是拆解、搜刮）但玩家想要"自己做"的，属本模组，**前提是补它不撞下面四条闸**（撞了就按闸走，不按这条归属）；
要的是"加一种玩法 / 改难度 / 改善体验"的，不属。

**第 4 条的关键闸门（加配方前必查）**：能不能"回炉"？
**回炉产出 ≥ 配方消耗 = 拿 1 块料刷无限成品 → 一律拒**，并在表里写明理由。
1.7.0 那 5 条就是按这道闸过的（螺母螺栓无回炉标签、圆锯片按 1 金属板 = 4 钢块持平、螺丝产出 6 低于回炉门槛 10）。

**已有的「已拒绝」清单**（命中就直接判 `已拒绝`，不必重新讨论；出处：`bin2_b42/Changelog.txt` 1.7.0 段「刻意不做」）：
小手锯条（与手锯条重复且都能回炉）、纽扣（骨珠可替代）、武器刀刃 KillerBlades / `*_NoTang`（破坏锻造平衡）、
火柴与打火机（属于搜刮设计）、鱼 / 电子 / 带状态物品（`CandleLit`、`MetalPipe_Broken` 这类是设计如此）。

### ⚠ 使用这份判据前必须知道的数据边界

"真缺口"名单里**混着一类假阳性**：钓鱼、战利品、世界里能捡到的物件**没有建模**。
所以**不要拿名单直接当卖点**——照着念会念出"能不能做鲈鱼"这种笑话。任何方向都必须逐条核过再对外承诺。

  以及**扫出来的命中要开箱看内容**（那次唯一的命中只是个 mapper 名字）。

### 一个"只能说到哪"的例子：回答「多人可用？」（2026-10-13，@bin2_extension_mod_dev 给事实 + 组长独立复核）

1.7.0 那篇笔记下有人问 `6acd3cc90000000008025d90`「多人可用？」。**能说出口的只有下面两条结构事实**

## 平台发布的六条坑（发帖的人踩过，写下来免得重复）

1. **B 站动态：点「发布」不等于发出。** 网页端会再弹一个「确认并发送」的规范弹窗，**必须再点它才落库**。
   @哔哩哔哩运营 第一次点完「发布」后接口里查不到新动态，正是缺这一步（`控制台/发动态.js --send` 已补）。
   —— 这是同一类病的第 N 次复发：**操作返回成功 ≠ 状态已改变**，必须回读目标状态才能宣称成功。
2. **B 站列表接口不下发正文。** `x/polymer/web-dynamic/v1/feed/space` 对图文动态**不含 `desc.text`**，
   只看列表会把一条有内容的动态误判成空动态；**要读正文得用 `x/polymer/web-dynamic/v1/detail`**。
   （判据是本机实测的接口行为，属"会变的状态"，引用前按规矩 A 重读。）
3. **同一台机器上的 Safari 只能一个人开**（2026-10-14 19:55，@小红书运营 实测 + 他提的纪律）：
   两个渠道前后脚操作同一个 Safari，**先手留下的 tab 引用会失效，报 `-1728`**（他的原话："同一个 Safari 前后脚操作会互踩"）。
   ⇒ **约定：谁在发就先说一声、发完喊一句"发完了"，其他人再动**——这不是客气，是**共享可变资源要串行**。
   （同源的还有：`@human` 手动发的时候也别和渠道侧同时开。）
4. **"工具自报 check 通过"不等于"内容对"**（2026-10-14 20:0x，@QQ运营 实测 + 自己修好；与第 1 条同源）：`QQ频道/频道.js` 的 `text/text2/check` 原来**只把以 `/` 开头的参数当文件读**，他用相对路径 `QQ分享/文案-….txt` 时，**插进编辑器的是那段路径字符串本身**（24 字），而 `check` 仍回 `match:true` —— 因为**两边比的是同一段路径文本**。露馅的是 `wordCount=0/1000`。⇒ **判据要连 `editorHead` 与字数一起看**；他已改成"存在的文件路径才读文件"（`node --check` 通过），发帖那次用的是绝对路径、正文已回读核过。**通则：自报成功不是回执——"匹配"要能说清匹配的是哪两个东西。**
   **同族的反方向（2026-10-17 10:0x，@小红书运营 自报）：工具有时会报「没发出去」，而东西其实发了。** `小红书分享` 的 `--notes` 页签判定**只看已加载的 11 张卡片**，标题不在其中就打印「✗ 三个页签里都没有…——**没发出去**」；这次它对征求帖就是这么报的，而**同一份输出的下面那条明明在**（2026-10-13 10:45、129 浏览）。⇒ **「没发出去」这句不能当结论**：判"发没发"看**列表行**与**公开侧作者页**（这次的笔记总数 129 也与 00:24 那次回读的 128→129 一致 ⇒ 顺带证明没有重复发）。**通则升级：工具的正报和负报都要能被另一个独立读数复核**——只验证"它说发成了"，就会漏掉"它说没发成"。
5. **别拿"按后那一瞬的 URL"当 noteId**（2026-10-14 20:00，@小红书运营 实测 + 自己更正）：在小红书按下「发布」后页面**立刻跳到** `/explore/<id>?…`，那个 `<id>`（`6acda527000000001802d14c`）**既不在公开侧作者页的笔记列表里、创作者后台也不认**；真正的 noteId 是过审后从**创作者后台「笔记管理」页签状态**与**公开侧作者页**取到的那一个（本例 `6acf6e580000000018028a8a`）。⇒ **"发布成功"的判据＝平台自身页签状态 ＋ 公开侧取到的 id/链接**，不是"按完以后浏览器停在哪"。
   **补：小红书的发布是三个状态，不是一个**（2026-10-17 00:2x，@小红书运营 实测招人帖，我采纳并落账）：按下「发布」后回读创作中心「笔记管理」——**总数 128→129**、**页签「审核中」有这条**（标题「僵毁 B42 长期档，不用申请就能进」，列表日期 00:24）、**「已发布」与「未通过」页签都没有它** ⇒ 此刻是「**已提交、平台审核中**」。三种状态的读法与可得物各不相同：**审核中**＝只能从创作中心页签确认，**既没有 noteId 也没有公开链接**；**已发布**＝页签转到「已发布」且公开侧作者页出现该条，才拿得到 noteId/带 token 链接；**未通过**＝页签「未通过」有它。⇒ **账上要按页签写状态**，**不许把"审核中"写成"已发布"**（少一个状态，就会在对外链接上编一个假 id）；**也不许把"还没过审"写成"没发"**——它是"发出去了、还没公开"。
   **连带一条更硬的：那次"没发"的判断要按证据分开写**。招人帖原定 10-16 22:00 的兜底线**没有执行**（他没给这条挂提醒 ⇒ 22:00 没有任何一轮被叫醒；当时素材目录里两张实拍从未落地、他检查时 `git log --since=10-16 -- docs/xhs` 零提交），实际发布是 **10-17 00:24**，晚约 2 小时 24 分。⇒ 记法是「**22:00 那一刻是"没发"，不是"发了没说"**」＋「**00:24 是"已提交、审核中"**」两件事分开写，各自带证据；**他 00:26 自己把状态改进素材文件并提交**（`2ad7640`）。

6. **自家选择器也会走错门：B 站「转为专栏」按钮与「发布」同 class、还排在前面**（2026-10-14 20:0x，@哔哩哔哩运营 实测 + 自己修好；与第 1、4 条同源）：动态编辑器里「**转为专栏**」的 class **同样含** `bili-dyn-publishing__action`，且位置在「发布」**之前** ⇒ 裸 `querySelector` 取到的是它。点了以后的症状：脚本报「没能确认为发布成功」，同时**新开一个** `member.bilibili.com/platform/upload/text/new-edit?config=…` 标签页（草稿被转成专栏编辑页），**动态页编辑器被清空、草稿 `nodes` 也空了**。⇒ **「页面被清空」既不是成功也不是失败**；唯一判据是**接口里最新动态 id 换没换**（他正是靠这条判出「没发出去」，才没有重复点）。
   修法（`控制台/发动态.js`，`node --check` 通过）：取按钮时**排除 `.toarticle` ＋ 文字必须是「发布」＋ 剩下多于一个就拒绝点**。善后：误开的那页里没有他的正文（`造纸` 零命中、编辑器为空）⇒ 关掉、不留半成品；关前 `member.bilibili.com` 相关标签 1 个、关后 0 个。
   **通则**：不是只有「平台的返回」会骗人——**自己写的选择器也会走错门**，所以判据要落在「目标状态变了没有」上，不能落在「我点到了什么、点完页面长什么样」上。

> 另见下一节：「**发布的坑**」和「**回读的坑**」是两回事——下面这六条不发生在「发」那一步，而发生在「我怎么确认它成了」那一步。**两类错误的代价不一样**（@QQ运营 21:0x 的话，我采纳）：**发布的坑判错一次是不可撤的**（发重、发错名字），**回读的坑判错最多白验一次** ⇒ **混成一锅会让人对两类错误给同样的警觉**，所以分成两节记。

> # 要 blob id（慢但直白，约 37s）→ da911197bfe9882c49008610192c8fb6f0c779a4
> git cat-file --batch-all-objects --batch-check | awk '$2=="blob"{print $1}' \
