版本 0.2.3 (2026-10-05)
- 修复：**面板把队友误报成「居民化被拒」并降级为跟随**（截图里那句
  「居民化被拒（resident（上游返回）），已降级为跟随」）
  * 现象：一栏雇员明明已经是营地的居民（在打水、巡逻、被基地保护），面板上却写着「岗位：跟随」，
    再点「居民」还被拒
  * 根因：面板右下角「应用岗位」发的就是"当前岗位"（`mode = pendingMode or contract.mode`），
    而岗位按钮当时是点一下立刻发 SetMode —— 于是"对已经是居民的人再应用一次居民"
    等于请求 Jeem 再收编一次。Jeem 的 `Residents.recruit` 对已经住进来的人会回
    `resident`（`Features/Residents/Server.lua:577`，真实含义是"**他已经是居民了**"），
    我们把它当失败处理：把契约降级成 follow、写上 note `resident:resident`，
    而且**写坏了缓存** —— 之后 `setMode` 只在"缓存说自己是居民"时才调 `leaveOne`，
    玩家再点多少次「居民」都回不去了
  * 附带表现：聊天栏连刷「招募操作已完成。」（同一份回包走了 dispatch 返回值与
    `sendServerCommand` 两条路），以及面板显示原始码「resident（上游返回）」而不是人话
  * 修法一（服务端幂等红线）：`Service.applyMode` 先读 Jeem 的**权威**状态
    （新增 `Jimmy.residentEntry` / `Jimmy.canManage`），已经是居民就直接算成功；
    `Jimmy.recruit` 同样先返回；`resident` 拒绝码再兜一层
  * 修法二（自愈）：`Maintain.reconcile` 每 30 秒（进世界第一次立刻）把契约岗位与
    `memory.jimmyResident` 双向对账——事实是居民就改回居民，事实不再是就落回跟随并写 `left_residence`
  * 修法三：`hireExisting` 在**扣款前**拦住已经是居民的 NPC（`already_resident`，不再白花签约金）；
    `dismiss`/`setMode` 都按权威状态决定要不要 `leaveOne`，Jeem 说 `busy` 时如实拒绝（`leave_busy`）
  * 修法四：`R.recruit` 收编的是整支小队 -> 新增 `Service.adoptJoined`，
    被同一次收编带进来的契约同步改成居民，不再留下"名册写跟随、人已是队友"的行
  * 修法五（文案）：`Text.lua` 穷举 Jeem 的拒绝码（resident / not_allied / no_beds / …），
    新增 19 个 CN/EN 翻译键（73 -> 92）；未知上游码仍走「（上游返回）」兜底
  * 修法六（客户端）：岗位按钮改成"选岗位 -> 点「应用岗位」"两步，`primaryAction` 不再重发当前岗位；
    结果码带 `*_degraded:<原因>`，提示从"招募操作已完成"改成"已处理（有降级）：<原因>"；
    `Net.apply` 用服务端单调 `seq` 去重，一份回包只提示一次
  * 修法七（可观测）：降级路径改用 `Config.always` 打日志（以前只在沙盒 DebugLog 打开时才打，
    线上只能靠猜），并带上 Jeem 自己的解释文本
- 测试：基模组 39/39、YeseMarket 变体 39/39 全绿。新增用例
  36（重复应用同一岗位必须幂等）、37（已是居民的人在付费前被拒）、
  38（Maintain 双向对账）、39（真失败仍降级，但原因必须是中文而不是上游码）
- 测试基建：`run.js` 现在把**真实的 CN 文案**注入 `Config.__cnText`，
  `MOCK.useCnTranslations()` 打开后可以直接断言"玩家实际读到的那句中文"；
  用例 19 增加了"选岗位不发命令、只有岗位变了才发"的流程断言
- 失败实验：把服务端的幂等预读与 `Jimmy.recruit` 的快速返回同时撤掉，用例 36 立刻变红
  （`mode_degraded:resident:…`、岗位变 follow、写出降级 note），与截图现象一致

版本 0.2.2 (2026-10-05)
- 修复：**雇下的人当不成队友**（游戏里提示「他们对你信任不足（需要同盟关系）」）
  * 现象：用面板雇了一名 NPC（跟随/守卫），之后想让他在你的营地当居民（队友）——
    无论是用 Jeem 自己的右键「邀请入住」还是面板里的「居民」岗位，都会被拒绝
  * 根因：那句提示来自 Jeem 本身（`[ALIFE-JIMMY]`），拦截点是它的同盟门槛
    `Residents.recruit` -> `R.isAlly`（`Features/Residents/Server.lua:581` / `:490-497`）。
    沙盒选项 `MakeAllied` 的说明写的是"签约后把声望垫到同盟档"，但代码**只在转居民那一步**垫，
    而且只用 `StandingService.addGroup`（小队路径）—— `memory.groupId` 拿不到时整段静默跳过。
    于是：先经 follow 雇下的人，之后永远过不了那道门
  * 修法一：**签约那一刻**就垫声望（`Service.markAllied`，所有岗位都走），
    Jeem 自己的右键邀请与面板的居民岗位检查的是同一个门槛，所以两条路一起通了
  * 修法二：改用 Jeem 的 `StandingService.add(key, factionId, delta, {groupId, groupPoints})`
    —— 阵营标签与小隊点数一起顶。档位是 hostile→careful→neutral→friendly→allied
    （thresholds {25,75,150,250}，clamp 400），从最坏情况要 ≥250 点，所以一次给到 400；
    小队那条只要 ≥50（`R.allyGroupPoints`）。`groupId` 拿不到时不再整段失效
  * 修法三：新增 `Jimmy.who(player)`，照 Jeem 自己的兜底顺序取玩家 key
    （`BaseAreas.who` → `playerKey` → `username`，同 `Features/DoorMarks/Marks.lua:326`）
- 测试：新增用例 35，断言的是**端到端结果**——"雇下之后这支小队真的能被收编成居民"；
  关掉沙盒开关时断言 `not_allied`（与游戏里一致）
- 测试基建（本轮真正的教训）：变体/基模组测试里 Jeem 的 mock 把同盟判定写成 `points >= 0`
  （几乎永远为真）且漏了阵营标签那条路，`StandingService` 也没有 `add`/`labelFor`/`groupPoints`
  —— 整条"垫声望"链路在离线测试里**从未被覆盖**，所以这个 bug 一路绿着进了游戏。
  现在 mock 逐条对齐 `Services/Standing.lua`（ladder/thresholds/clamp/add/labelFor/groupPoints）
  与 `R.isAlly`（`allyGroupPoints = 50`）。已做失败实验：撤销修复后用例 35 立刻以 `not_allied` 变红

版本 0.1.1 (2026-10-05)
- 修复（玩家实测反馈：按钮/文字错位）：
  1. 招募面板右侧的说明文字会压住「跟随/守卫/居民」按钮行（窗口越矮越明显）。
     原因：模式按钮固定在 `listTop + 118`，而文本从上往下不限行数地画。
     修法：右侧面板改成**自下而上**排版 —— 先从底部预留「模式行 + 主按钮 + 次按钮」两块固定高度，

     原因：原实现只把「社区中心」按钮当锚点，而它在社区中心功能关闭时根本不存在，
     于是回退到"贴右边缘"，正好压住右侧那排视图切换按钮。
     修法：把「社区中心 / 概览首页 / 卡片」三个锚点都收集起来取**最左**，贴在它左侧；
     一个都没有时贴左边缘，绝不与右侧控件抢位。
- 新增回归测试：把版面几何当契约来测（800x600 / 1200x700 / 520x420 三种尺寸下断言

  已做过失败实验：把文本裁剪改回旧行为，三条断言立刻变红。

版本 0.1.0 (2026-10-05)
- 初始版本：为「橙子社区经济」增加 NPC 招募功能，兼容 Project A-Life Jeem Extension
- 功能：
  * 招募面板（`OrangeTradingMod.UIPageRegistry` 公开页面 API 注册，页面 id `bin2NpcRecruit`）
    与首页入口按钮；另加 Ctrl+Alt+N 热键（该模组自身全库没有任何按键绑定，不会冲突）
  * 收编：花钱把身边已有的 A-Life NPC 签下来（服务端校验距离/名额/归属/敌对）
  * 中介派遣：`ActorRegistry.create` + `SpawnService.request` 现造一名友好 NPC；
    生成失败自动全额退款，不会出现「花了钱没人」
  * 三种岗位：跟随（A-Life 原生 follow）/ 守卫（hold + 锚点）/ 居民（Jeem `Residents.recruit`）
  * 名册：切换岗位、解雇、阵亡自动释放名额、日薪与欠薪宽限期
- 依赖：必需 `OrangeCommunityEconomy`；需要 `ProjectALifeNPCs`；可选 `ProjectALifeJimmy`
- 安全设计：
  * 钱只走 `OrangeTradingModServer.Pay` / `AddCoins`（服务端权威，客户端不传价格）
  * 自带限速与 requestId 去重（橙子经济的 action_request_guard 是白名单制，第三方塞不进去）
  * 防人口回收：雇佣期间给 NPC 写 `memory.persistent` + `memory.admin.persistent`
  * 读档后自动重下 follow/hold 指令（A-Life 的 orders 是内存表，不持久化）
  * 改动状态一律先扣款后落地，失败按路径退款或降级（降级会写进契约备注并显示在面板上）
- 未修改任何第三方文件；不带任何 A-Life / Jeem 的 Lua 副本；不占用它们的网络 module
- 已知限制：
  * 尚未在游戏中完整跑过验证（只做了 Lua 语法检查 + 离线逻辑测试 + 工坊探针校验）
  * Jeem 的居民招募按「小队」收编，转居民时可能把整支小队带进营地
  * 与其它 NPC 模组（Bandits2 等）的共存未测试
  * 未做真实上传验证；`workshop.txt` 首次上传不带 `id=`，`visibility=private`，验证无误后再改 public
